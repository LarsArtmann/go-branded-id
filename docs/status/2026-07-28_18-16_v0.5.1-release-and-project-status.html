Bottom Line

v0.5.1 is out and the source archives are clean. The immediate crisis (a tracked binary inflating release tarballs ~10x) is resolved. However, the project still carries significant hygiene debt: uninvestigated security alerts, failing docs validation CI, unpinned actions, and incomplete test coverage for new sentinel errors. Nothing is on fire, but several items are smoldering.

04Totally Fucked Up!

Shipped Defect

v0.5.0 source archives shipped a tracked namer binary

git ls-tree -r v0.5.0 → 100755 blob ... namer

The v0.5.0 release tarball was ~2.09 MB because it included a build artifact. v0.5.1 is the fix, but this should never have been committed. The root cause was missing automated enforcement: .gitignore existed but the binary was force-added or added before the ignore rule.

Mitigated in v0.5.1. Long-term fix is a CI guard against tracked binaries plus a release dry-run that inspects source archives before the tag is pushed.
Security

Two Dependabot vulnerabilities are uninvestigated

GitHub reported 1 high + 1 moderate on the v0.5.0 push

We do not know if these affect runtime users, the website, or dev-only dependencies. They have been sitting in the TODO list since v0.5.0.

CI

Docs validation CI is failing

.github/workflows/validate-docs.yml

md-go-validator@latest module v1.2.0 exists but the root package does not. The install path likely needs to point to cmd/md-go-validator. This means every push currently fails docs validation unless it is skipped.

Security

All GitHub Actions use tag pins instead of commit SHAs

17 findings across go.yml, release.yml, validate-docs.yml

Tags can be moved to malicious code. BuildFlow flags this as high-severity. For a library consumed by 14 downstream repos, this is a supply-chain risk.

Quality

26 structural linter findings from BuildFlow

go-structure-linter output during pre-commit

Includes the root-package-files rule flagging errors.go, id_*.go as "should be in /internal/ or /pkg/". Some may be false positives for an intentional flat single-package library, but they are currently un-suppressed and create noise on every commit.

05What We Should Improve

1. Make binary leaks impossible, not unlikely

Add a CI check (and ideally a pre-commit hook) that fails if any tracked file matches executable/binary heuristics at the repo root or in build output directories. The existing file-size-check in BuildFlow might catch large files, but a targeted git ls-files | xargs file check would be explicit.

2. Investigate Dependabot alerts before the next release

Run gh api repos/LarsArtmann/go-branded-id/dependabot/alerts, determine affected dependency paths, and either patch or document why they are dev-only / non-exploitable. Do not ship v0.5.2 with these still open.

3. Pin actions and add nix flake check to CI

Converting all @vN references to full commit SHAs removes the supply-chain warning. Adding nix flake check to go.yml and release.yml closes the gap between local Nix validation and CI.

4. Close the sentinel-error testing gap

Add table-driven errors.Is tests for ErrUnsupportedType, ErrCannotScan, ErrInsufficientData, ErrInternal, and ErrNilReceiver. This is a 1-hour task with high public-API value.

5. Sync public website with releases

The website is the public face of the library. Changelog and feature docs for v0.4.0–v0.5.1 should be updated before DNS for branded-id.lars.software is considered complete.

6. Decide on root-package-files linter policy

Either accept the flat-package design and suppress the rule, or redesign the module layout. Leaving 24 warnings unaddressed trains everyone to ignore BuildFlow output.
