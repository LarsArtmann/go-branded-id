## d) TOTALLY FUCKED UP

### 1. Ran `nix fmt` mid-release (cascading damage)

**What:** During release prep, I ran `nix fmt` to fix a pre-existing `treefmt-check` failure. This was a **mistake** — `nix fmt` runs golines, which re-wrapped long `fmt.Errorf`/`errors.New` lines. The wrapping moved `//nolint:err113` comments from the statement line to the closing `)`, making them ineffective. `nolintlint` then flagged them as unused, BuildFlow's repair removed them, and `err113` fired 7 times.

**Why it was stupid:** The AGENTS.md explicitly warns that `nix fmt` causes problems in this repo. The `treefmt-check` failure was pre-existing and NOT in CI (`release.yml` only runs `go build`, `go test -race`, `golangci-lint`). I introduced a new problem to fix one that didn't matter for the release.

**Impact:** Cost ~30 minutes of debugging and required the full sentinel error refactor. The refactor itself was good work, but doing it mid-release under time pressure was reckless.

### 2. Forgot to sign the tag initially

**What:** First `git tag -a v0.5.0` created an unsigned annotated tag. AGENTS.md says "Tags must be signed (SSH) and annotated." Had to delete and recreate with `-s`.

### 3. Let the auto-git daemon commit with garbage messages

**What:** The auto-git daemon committed intermediate states with malformed conventional commit messages:

- `1cbdd8c` — "(id): add comprehensive serialization support across formats"
- `a85ebbb` — "feat(id): refactor branded ID encoding across binary, SQL, and text formats"
- `f46fab1` — "): add branded ID type with multi-format serialization support"
- `f749618` — "feat(id): implement standard serialization interfaces for branded IDs"

These commits contain unrelated changes lumped together (formatting + sentinel refactor + changelog). The history is noisy. I should have committed my changes faster to beat the daemon, or staged them atomically.

### 4. Didn't check CI before declaring "done"

**What:** I said "v0.5.0 released" without confirming the GitHub Actions release workflow succeeded. The tag push triggers CI, but CI could fail (e.g., if `golangci-lint-action@v7` behaves differently in CI than locally).

## e) WHAT WE SHOULD IMPROVE

### Process

1. **Never run `nix fmt` during a release.** The treefmt/golines-vs-golangci-lint tension is a known pre-existing issue. Fix it outside of release windows.
2. **Fix the golines-vs-nolint conflict at the root.** Golines should not move `//nolint` directives off the line they're suppressing. This is a tooling configuration issue: either configure golines to keep inline comments on the same line, or stop using `nolint` directives on long lines.
3. **Commit faster or disable the auto-git daemon during releases.** The daemon's garbage commit messages pollute history. Either commit atomically before the daemon fires, or pause it during release work.
4. **Verify CI success before declaring a release done.** Push the tag, then `gh run watch` or check the Actions tab.
5. **Run the sentinel error refactor BEFORE the release, not during.** The `//nolint:err113` suppressions were a known smell. Fixing them should have been a pre-release cleanup task, not a mid-release emergency.

### Code

6. **The golines line-wrapping creates a fragile situation.** Multi-line `fmt.Errorf("%w: ...", sentinel, args...)` calls will get re-wrapped by golines, and the `%w` verb stays valid but the code gets ugly. Consider a helper function for wrapping errors with context to avoid this entirely.
7. **`ErrNotOrdered` message changed.** The original was `"id: Compare requires an ordered type (int, uint, or string)"`; the new one is `"id: Compare requires an ordered type"`. This is a (minor) breaking change in error message text. The test uses `errors.Is` so it passes, but any consumer parsing the message string would break.
8. **`errors.go` is generic-named.** It could collide with consumer expectations or future Go stdlib conventions. Consider `id_errors.go` to match the `id_<feature>.go` naming pattern — though `errors.go` is also a common Go convention.
